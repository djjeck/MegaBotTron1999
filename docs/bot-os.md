# MegaBotTron1999: principles and decisions

Documented as of 12 Nov 2026. A design guide for a plugin-based system that connects to chat
networks, parses the messages of the game bots that run there, and acts on them: an empty shell
installed in a container, extended by plugins. The shell knows no game: games, and what plays them,
are modules on top of it (D49).

This document is the yardstick for the work: a new decision is checked against the principles below,
and a decision that breaks one either changes the principle here, with its reason, or is dropped.
Decisions are logged in §4 with their status: **decided** by the author, or **proposed** and waiting
for the author's word. The numbers are stable, so that code and other repositories can cite them; a
decision that only concerned one private deployment is kept as a numbered placeholder.

## 1. What it is

- **The shell (core):** loads plugins, holds the accounts and their secrets, routes messages and
  events, runs the outbox and the scheduler, keeps each plugin's state, and serves the web UI and
  the agent interface. It knows nothing of any game.
- **Plugins**, of these kinds (one plugin may be more than one):
  - **Connector:** a network, bound to one account: Telegram as a user, Telegram as a bot, IRC
    (through ZNC), and later email, an LLM's API, a standalone UI.
  - **Parser:** the messages of one game bot into typed events of that game.
  - **Actor:** sends commands to a game, on a schedule or in answer to events.
  - **Stats and commands:** reads events, keeps a ledger or counters, answers commands, offers UI
    pages and status widgets.
  - **Agent:** a supervisor, such as an LLM, which reads and controls other plugins through their
    declared interfaces.
  - **Simulator:** a model of a game, for developing and tuning actors (P15). It need not run inside
    an instance.
- **An instance** is one deployment of the shell with its plugins, owned by one person (D19).

The plugin API (the manifest, the lifecycle, what the core gives a plugin, and the shell's own
plugins) is in [bot-os-api.md](bot-os-api.md).

## 2. Principles

**P1. Trusted plugins only.** Plugins run in the shell's process, with no sandbox, so only code its
owner has reviewed runs. Since D49 the store of plugins is the data volume: the owner installs
modules there, and the next start loads them; nothing is downloaded at runtime but what the owner
asks to install (a module from a GitHub link, D67), and no agent installs anything. A plugin runs
with the shell's full rights: it can read every secret the process holds and send as every account
it is connected to. Run only plugins you have read.

**P2. Automation is its owner's.** The shell is public. What plays a game (actors, tactics, their
tuning) is a module of its owner's, public or private as its owner decides; the shell neither ships
nor requires any.

**P3. One command per bot.** An actor talks to one game bot, with that bot's own command, addressed
to it (`/command@BotName` in a group, which the other bots ignore), and in a private chat with the
bot where the bot supports it. No command is sent to play several bots at once: each bot has its own
policy, and its plugin follows it.

**P4. People are responsible for their automation.** The shell does not try to enforce a game's
etiquette: rules change, and whoever controls an instance can remove any limit. Each owner runs
their plugins at their own risk, and each group polices its members. The shell does handle the
networks' technical limits (Telegram's flood waits, IRC's flood and clone limits), which are
protocol, not etiquette.

**P5. Parser drift is part of the foundation.** Every message that a parser claims but cannot read
is reported (to the event log, the UI and the owner) with the text that failed. When a plugin that
acts meets an error it cannot recover from, the shell stops it (D64), and everything that depends on
its events (D65), until the owner looks. Plugins that only read keep running and keep reporting.

**P6. Each plugin owns its state.** A plugin reads and writes only its own storage. A plugin that
needs another's data or actions declares it in its manifest, and gets it through the other's
declared interface, which is reviewed with both. No plugin reads another's files or tables.

**P7. Types are per game, and games can meet.** Each game registers its event and command types
under its own namespace (`dice.roll`, `quest.turn`). A plugin that spans games (one command with
stats from several) declares the namespaces it consumes, as in P6. Games are mostly apart, but
nothing in the shell assumes it.

**P8. State survives a redeploy.** All important state can be serialised and is restored at start:
plugin state, the scheduler's timers, settings, and each node's state (D64). There is no hot reload:
a change is a new image or new modules, and a restart.

**P9. Secrets are kept the standard way.** Session strings, tokens and API keys are never in the
repository, the image or the logs. They are not in environment variables where avoidable, because
those show in `docker inspect` and the process environment. They reach the container as Docker
secrets, are encrypted at rest when the shell stores them, and are readable only by the shell's
user. Plugins never see a credential: a connector holds it and plugins get a handle to the
connector.

**P10. What a plugin sends is held by the shell:** each node is enabled, disabled by the owner,
stopped by exception, or inactive for what it needs, and each chat-out edge sends for real or as a
dry run, logged as sent; the shell enforces them on everything the plugin sends. A new node starts
disabled and a new chat-out edge a dry run, only the owner raises a state, and the states survive
restarts (amended by D64, which replaced the modes `read-only`, `dry-run` and `live`).

**P11. One interface for people, commands and agents.** Each plugin describes its commands, actions
and state with typed schemas (zod). The web UI, chat commands and an MCP-like interface for agents
are all built from those descriptions. An agent session is granted an explicit subset of connectors
and plugin interfaces, and sees nothing outside that subset: not in its tool list, not in the state
it reads.

**P12. One language: TypeScript,** on Node 24 running the sources (type stripping), with strict
types, Vitest, ESLint and Prettier.

**P13. The API stays open until launch.** Until the first official launch, the plugin API changes
freely, together with every plugin that uses it. At launch it is locked and versioned; after that,
breaking changes need a new major version.

**P14. Design first, and extract from working code.** These principles come first. The code was
extracted from a client that already worked, not written from scratch, and every step leaves a
deployed instance working.

**P15. Simulation is a first-class plugin kind.** Developing an actor means running it against a
simulated game. Simulators may run as development tools outside an instance. A game's grammar (its
message wording, its rules) is shared between parser and simulator as library code, not as live
modules.

**P16. Two kinds of UI.** An admin part, for deployment and system status: the instance, its
accounts, its plugins and their states, health, the drift reports of P5. And pages contributed by
plugins: widgets with a plugin's own status on the dashboard, and full pages where a plugin has more
to show.

**P17. Composition is a typed graph.** Each plugin instance is a node, with input ports (what it
consumes) and output ports (what it produces), each of a port type the core defines: a chat
connection, a game's events, a plugin's interface. A generic port type is bound to a specific
instance by an edge, with its details (an IRC connection to `#lobby`, a private chat with a bot).
The instance's wiring is that graph, kept as data: the web UI draws it and edits it, and the edges
are the permissions (P6). One plugin may be used more than once, and a plugin may wrap or extend a
base one. This makes clear which module talks to which, to people who do not write code too.

## 3. Architecture in outline

- **Accounts** are first-class. Every connector is bound to one account, every event says which
  account saw it, and every action says which account sends it. One person may have several: a
  Telegram user account, a Telegram bot and an IRC nick.
- **The bus** carries inbound messages from connectors to parsers, and typed events from parsers to
  whatever declared it consumes them (P6, P7).
- **The outbox,** one per account: every action goes through it. It enforces the sender's state and
  its edge's dry run (P10, D64), queues and spaces the sends, handles the network's flood limits
  (P4), and matches replies to the command that caused them where the bot makes it possible (a
  reply-to, a mention of the player, a time window).
- **The scheduler** keeps timers durably (P8): "play again in 17 minutes" survives a redeploy.
- **The store** keeps each plugin's state in its own namespace (P6), with migrations when a plugin
  is upgraded.
- **The manifest** of each plugin names its kinds, the game namespaces it registers and consumes,
  its ports, its config schema and secrets, and its interface (P11).
